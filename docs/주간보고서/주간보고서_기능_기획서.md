1. **팀별 주간 보고서** — 한 팀 범위. 팀원과 팀장이 본다.
2. **전체 주간 보고서** — 3팀 합산. 관리자가 본다.

## 3. 데이터 모델 변경

### 3.1 프로젝트 (결정 3, 7)

자유 텍스트가 아니라 별도 테이블 + 외래키로 둔다. 프로젝트는 반드시 한 팀에 속한다.

```sql
CREATE TABLE public.projects (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name TEXT NOT NULL,
    team_id TEXT NOT NULL REFERENCES public.teams(id) ON DELETE CASCADE,
    is_active BOOLEAN DEFAULT TRUE NOT NULL,
    created_at TIMESTAMPTZ DEFAULT TIMEZONE('utc'::text, NOW()) NOT NULL,
    UNIQUE (team_id, name)
);

ALTER TABLE public.tasks
  ADD COLUMN project_id UUID REFERENCES public.projects(id) ON DELETE SET NULL;

CREATE INDEX idx_tasks_project_id ON public.tasks(project_id);
```

**왜 텍스트 컬럼이 아닌가.** 규칙 13이 다루는 표기 흔들림(띄어쓰기 차이 등)을 원천에서 없앤다. `UNIQUE` 제약이 중복 표기를 막으므로, 사후에 "유사 표기를 통일할까요" 하고 물을 일 자체가 생기지 않는다.

**유일성 범위는 팀 안이다** (결정 7). `UNIQUE (team_id, name)`이므로 팀이 다르면 같은 이름의 프로젝트가 존재할 수 있고, 둘은 **별개 프로젝트로 취급한다.** 예: 개발팀 "리뉴얼"과 디자인팀 "리뉴얼"은 합치지 않는다.

**규칙 12의 3분류가 2분류로 줄어든다.** 텍스트 파싱이 아니므로 "추정" 그룹이 필요 없다.

- 확정 = `project_id` 있음
- 기타 = `project_id` NULL

**업무와 프로젝트의 팀은 같아야 한다.** `tasks.team_id`와 `projects.team_id`가 어긋나면 안 된다. 저장 시 검증한다(UI 선택 목록을 해당 팀 프로젝트로 제한 + DB 트리거 또는 CHECK).

**기존 업무 소급 입력** (결정 10). 스키마 적용 직후 같은 마이그레이션에서 실행한다.

```sql
INSERT INTO public.projects (name, team_id) VALUES
  ('주간업무 대시보드', 'development'),
  ('주간업무 대시보드', 'design');

UPDATE public.tasks t
   SET project_id = p.id
  FROM public.projects p
 WHERE p.team_id = t.team_id
   AND p.name = '주간업무 대시보드';
```

대상은 현재 `tasks` 2건 전부다. `supabase 연결하기`(개발팀 / 실타래), `와이어프레임 작업`(디자인팀 / 김드림).

팀이 다르므로 이름은 같아도 별개 프로젝트 2건이 된다 (결정 7).

🟡 **UPDATE에 task id를 박지 않았다.** 두 팀의 모든 업무를 대상으로 한다. 지금은 그 집합이 정확히 위 2건이지만, 마이그레이션 적용 전에 새 업무가 들어오면 그것도 함께 묶인다. 적용 직전 `SELECT count(*) FROM tasks WHERE team_id IN ('development','design')`으로 2건인지 확인하고 실행한다.

### 3.2 이슈 (결정 2, 6)

단일 필드로 둔다.

```sql
ALTER TABLE public.tasks
  ADD COLUMN issue_note TEXT;
```

`issue_note IS NOT NULL` 이면 이슈다. **비어 있으면 이슈 없음이다** (결정 6).

**왜 `is_issue BOOLEAN` + `issue_note TEXT` 두 필드가 아닌가.** 두 필드는 서로 어긋난 상태(플래그는 켜져 있는데 내용이 비었음)를 만들 수 있다. 규칙 9는 이슈 표에 "막힌 내용"을 반드시 요구하므로, 내용 없는 이슈는 애초에 성립하지 않는다. 필드 하나면 그 상태를 표현할 방법이 없다.

**이슈는 `status`와 직교한다.** 한 업무가 "진행중이면서 이슈"일 수 있다. 보고서에서 어느 쪽으로 셀지는 3.3에서 확정한다.

**해소 처리** (결정 6): 필드를 비우면 이슈가 풀린다. `RESOLVED` 같은 별도 상태를 두지 않는다.

🟡 **알려진 한계.** 보고서는 마감 시점의 스냅샷이다(4.3). 주중에 생겼다가 마감 전에 해소된 이슈는 그 주 보고서에 남지 않는다. 이슈 이력을 주 단위보다 촘촘히 남기려면 별도 이력 테이블이 필요하며, 이번 범위에는 넣지 않는다.

### 3.3 상태 → 보고서 분류 매핑 (규칙 1, 2)

웹앱 상태는 4종이고 보고서 상태는 3종이다. 코드가 그때그때 판단하지 않도록 여기서 표로 확정한다.

| DB 조건 | 보고서 분류 | 우선순위 |
|---|---|---|
| `issue_note IS NOT NULL` | **이슈** | 1 (status보다 우선) |
| `status = 'DONE'` | **완료** | 2 |
| `status IN ('TODO','IN_PROGRESS','IN_REVIEW')` | **진행중** | 3 |

우선순위를 두므로 한 업무가 두 곳에 중복 집계되지 않는다.

`IN_REVIEW`를 진행중에 넣는 것은 **이 표로 확정한 결정**이다. 규칙 2가 금지하는 것은 코드나 AI가 그때그때 임의로 판단하는 것이며, 문서로 고정한 매핑은 임의 판단이 아니다.

미분류는 4.5에서 따로 정의한다.

## 4. 보고서 생성 규칙

### 4.1 주차 키

기존 마감 함수와 같은 ISO 주차 키 `IYYY-"W"IW`를 쓴다 (예: `2026-W35`). 별도 키를 만들지 않는다.

### 4.2 데이터 소스

🔴 **`cycle_week`만 믿고 완료 건을 세면 안 된다.**

로그 불일치를 고치지 않기로 했으므로(결정 1), 복구된 업무에는 `cycle_week`이 남아 있고 `is_archived`만 false인 행이 계속 생긴다. 2026-W35에 실제로 2건 있다.

방어 방법은 두 조건을 함께 요구하는 것이다.

| 집계 항목 | 조건 |
|---|---|
| **완료 건** | `is_archived = TRUE AND cycle_week = :week` |
| **진행중 / 이슈 건** | `is_archived = FALSE` (마감 직후 시점의 잔여 업무) |

`is_archived`를 함께 요구하면 복구된 행은 자동으로 빠진다. 현재 DB의 2건은 완료로 잡히지 않으며, 이는 실제 상태와 맞다.

#### 🔴 주차 태깅이 한 주 밀린다 — 자동 생성 전 반드시 결정해야 함

`execute_weekly_archive`는 `cycle_week`을 **실행 시점의 주차**로 찍는다(`TO_CHAR(NOW(), 'IYYY-"W"IW')`, 마이그레이션 파일 78행).

cron은 월요일 00:00 UTC에 돈다(`vercel.json`). 그 시각은 이미 **새 주의 첫날**이다. 실측으로 확인했다.

| 시각 | `TO_CHAR(NOW(),'IYYY-"W"IW')` |
|---|---|
| 2026-08-31 00:00 UTC (cron 실행 시각) | `2026-W36` |
| 그 하루 전 | `2026-W35` |

즉 **W35 한 주 동안 완료한 업무가 `cycle_week = '2026-W36'`으로 저장된다.** 지금까지는 사람이 금요일에 수동 실행해서(2026-08-29, W35) 드러나지 않았다.

마감 직후 자동 생성(결정 5)으로 가면 매주 부딪힌다.

#### 해결 — A안 확정 (결정 8)

`execute_weekly_archive`가 **전날 기준**으로 주차를 찍게 고친다. 월요일 새벽에 돌아도 지난 주로 태깅된다.

기준 시각은 기존 스키마 관례대로 **UTC**를 쓴다. KST 기준과 비교해봤으나 cron 실행 시각과 통상적인 수동 실행 시각에서 결과가 모두 같아, 타임존을 새로 들일 이유가 없다.

**적용할 변경 — 두 군데다.** `20260829083033_create_weekly_archive_system.sql`의 함수 본문과 `EXCEPTION` 블록 양쪽에 같은 식이 들어 있다. 한쪽만 고치면 실패 로그의 주차가 어긋난다.

```sql
-- 본문 (78행 부근)
- v_cycle_week := TO_CHAR(NOW(), 'IYYY-"W"IW');
+ v_cycle_week := TO_CHAR(TIMEZONE('utc', NOW()) - INTERVAL '1 day', 'IYYY-"W"IW');

-- EXCEPTION 블록
- gen_random_uuid(), TO_CHAR(NOW(), 'IYYY-"W"IW'), 'FAILED', ...
+ gen_random_uuid(), TO_CHAR(TIMEZONE('utc', NOW()) - INTERVAL '1 day', 'IYYY-"W"IW'), 'FAILED', ...
```

**적용 방식**: 이미 적용·커밋된 마이그레이션 파일을 고치지 않는다. `CREATE OR REPLACE FUNCTION` 전문을 담은 **새 마이그레이션 파일**을 추가한다.

**동작 확인 (DB 실측)**

| 실행 시각 (KST) | 현행 | A안 적용 후 |
|---|---|---|
| 월 09:00 — cron | `2026-W36` | **`2026-W35`** |
| 토 17:35 — 기존 수동 실행 | `2026-W35` | `2026-W35` (변화 없음) |
| 일 23:00 | `2026-W35` | `2026-W35` (변화 없음) |
| 수 14:00 | `2026-W36` | `2026-W36` (변화 없음) |

바뀌는 것은 **월요일 실행뿐이다.** 화요일 이후 실행은 실행 주차 그대로 태깅된다.

**결정 1(불일치 방치)과는 별개 사안이다.** 결정 1은 이미 생긴 W35 데이터를 손대지 않는다는 것이고, 이건 앞으로의 태깅 규칙이다. 기존 로그 1건은 그대로 둔다.

🟡 **소급 적용하지 않는다.** 기존 `weekly_archive_logs`와 `tasks`의 `cycle_week` 값은 건드리지 않는다. 함수 교체 이후 실행분부터 새 규칙이 적용된다.

### 4.3 마감 직후 자동 생성 (결정 5)

기존 cron 라우트(`src/app/api/cron/weekly-archive/route.ts`)를 확장한다.

```
cron (월 00:00 UTC)
  → execute_weekly_archive 실행
  → 성공 시 이어서 보고서 DRAFT 생성
      · 팀별 3건 (planning / design / development)
      · 전체 1건
  → 실패 시 보고서를 만들지 않고 종료. 로그만 남긴다
```

**순서가 중요하다.** 마감이 먼저 끝나야 그 주 완료 건이 `is_archived = TRUE`가 되고, 4.2의 완료 조건이 성립한다. 마감 전에 만들면 완료가 0건으로 나온다.

**재생성**: 관리자가 수동으로 다시 생성할 수 있다. `DRAFT` 상태면 덮어쓰고, `CONFIRMED`면 거부한다. 사람이 확정한 보고서를 자동 재생성이 덮지 않게 한다.

🟢 **cron 미실행 원인은 밝혀졌다.** 2026-08-31 13:00 UTC 기준 `weekly_archive_logs`에 자동 실행(`executed_by IS NULL`) 행은 0건, `FAILED` 행도 0건이다. 원인은 순서였다.

| 시각 (UTC) | 사건 |
|---|---|
| 2026-08-31 00:00 | cron 예정 시각 |
| 2026-08-31 10:39 | `0c1a444` 커밋 — `vercel.json`에 cron 스케줄을 **처음** 추가 |

예정 시각이 스케줄 등록보다 10시간 40분 빨랐다. 실행될 수 없었다. 버그가 아니다.

`0c1a444`는 현재 `main` HEAD이고 `vercel.json`과 cron 라우트가 모두 main에 있다. 배포가 정상이라면 **첫 자동 실행은 2026-09-07 00:00 UTC**다.

🔴 **그래서 4.2의 주차 태깅 수정은 2026-09-07 이전에 적용해야 한다.** 현행 함수로 09-07 cron이 돌면 W36 한 주의 완료분이 `2026-W37`로 태깅된다.

**확인하지 못한 것**: Vercel 대시보드에서 cron이 실제로 등록됐는지는 보지 않았다. 09-07 이후 `weekly_archive_logs`에 자동 실행 행이 생기는지가 최종 확인이다.

### 4.4 보고서 스냅샷 저장 (결정 4, 규칙 10, 14)

```sql
CREATE TABLE public.weekly_reports (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    cycle_week TEXT NOT NULL,
    scope TEXT CHECK (scope IN ('TEAM','ALL')) NOT NULL,
    team_id TEXT REFERENCES public.teams(id) ON DELETE CASCADE,  -- scope='ALL'이면 NULL
    status TEXT CHECK (status IN ('DRAFT','CONFIRMED')) DEFAULT 'DRAFT' NOT NULL,
    summary_text TEXT,                                            -- 사람이 직접 작성
    summary_written_by UUID REFERENCES public.profiles(id) ON DELETE SET NULL,
    confirmed_at TIMESTAMPTZ,
    payload JSONB DEFAULT '{}'::jsonb NOT NULL,                   -- 집계 결과 + task id 목록
    created_at TIMESTAMPTZ DEFAULT TIMEZONE('utc'::text, NOW()) NOT NULL
);
```

🔴 **위 `UNIQUE (cycle_week, scope, team_id)`는 쓰지 않았다. 동작하지 않는다.**
Postgres는 UNIQUE 제약에서 NULL을 서로 다른 값으로 취급한다. `scope='ALL'`인 행은
`team_id`가 NULL이므로, 한 주차에 전체 보고서가 여러 건 생길 수 있다.
부분 유니크 인덱스 두 개로 나눠야 실제로 1건씩 보장된다.

```sql
CREATE UNIQUE INDEX uq_weekly_reports_team
  ON public.weekly_reports(cycle_week, team_id) WHERE scope = 'TEAM';
CREATE UNIQUE INDEX uq_weekly_reports_all
  ON public.weekly_reports(cycle_week) WHERE scope = 'ALL';
```

`scope`와 `team_id`가 어긋나지 않도록 CHECK 제약도 함께 걸었다.
`ALL`이면 `team_id IS NULL`, `TEAM`이면 `team_id IS NOT NULL`이다.

**요약은 사람이 쓴다** (결정 4). AI 자동 생성을 넣지 않으므로 생성 시점의 `summary_text`는 비어 있고, 담당자가 직접 채운 뒤 확정한다.

**왜 스냅샷 테이블이 필요한가. 세 가지 이유가 있다.**

1. **지난 주 조회가 정확해진다.** 진행중·이슈는 마감 시점 스냅샷이라, 저장하지 않으면 지난 주 보고서를 열었을 때 그 주가 아니라 오늘 상태가 나온다. 생성 이후에는 라이브 쿼리가 아니라 `payload`를 읽는다.
2. **반복 이슈 판정의 근거가 된다** (규칙 10). `tasks` 행은 주가 바뀌어도 같은 행이라 이력이 남지 않는다. 결정 6으로 `issue_note`를 비우면 이슈 흔적이 사라지므로, 스냅샷이 유일한 이력이다. 수기 절차의 `이전주_이슈기록.md` 역할을 한다.
3. **확정 상태를 기록한다.** `DRAFT`는 요약 미작성 또는 검토 중, `CONFIRMED`는 확정이다.

**반복 이슈 판정 방법** (규칙 10): 지난 주 스냅샷의 **요약 문장을 읽지 않는다.** `payload`에 저장된 task id 목록과 이번 주 이슈 목록을 행 단위로 직접 대조한다. 문서에 결론이 적혀 있어도 그것을 근거로 삼지 않는다.

### 4.5 미분류 (규칙 2, 8 변형)

DB의 `CHECK` 제약 때문에 상태가 비어 있는 행은 존재할 수 없다. 수기 절차의 "태그 오타 → 미분류"는 그대로 옮길 수 없다.

대신 **집계에서 빠지는 항목**을 미분류로 모은다.

| 조건 | 사유 표기 |
|---|---|
| `assignee_id IS NULL` | 담당자 미지정 — 팀원별 집계 불가 |
| `cycle_week IS NOT NULL AND is_archived = FALSE` | 마감 데이터 불일치 (현재 2건 해당) |
| `project_id`의 팀과 `tasks.team_id` 불일치 | 프로젝트 소속 오류 (3.1 검증 우회 시) |

사유를 함께 표시한다. **임의로 보정하지 않는다.**

## 5. 화면 설계

### 5.1 팀별 주간 보고서

- **경로**: `/teams/[teamId]/report?week=2026-W35`
- **열람 권한**: 해당 팀 소속 member + admin. 기존 `tasks` RLS와 같은 범위다.
- **작성 권한** (결정 9): 요약 작성과 확정은 **해당 팀 소속 member + admin**이 한다. 열람 범위와 같다.
  - **팀장 역할은 두지 않는다.** `profiles.role`의 CHECK 제약이 `member` / `admin` 2종뿐임을 실측으로 확인했다. 팀장을 표현하려면 스키마와 기존 RLS 정책을 함께 손봐야 해서 이번 범위에 넣지 않는다.
  - 🟡 **한계**: 같은 팀 member 누구나 팀 요약을 쓰고 확정할 수 있다. 다른 사람이 쓴 요약을 덮어쓰는 것도 막지 않는다. `summary_written_by`에 작성자가 남으므로 누가 썼는지는 추적되지만, 권한으로 막지는 않는다.
- **문서 순서 고정** (규칙 15):
  1. 이번 주 요약 (사람이 작성)
  2. 제출 현황
  3. 상태별 요약
  4. 이슈 상세 (반복 / 신규 구분)
  5. 팀원별 건수
  6. 프로젝트별 묶음 (기타 포함)
  7. 미분류 항목
- **제출 현황** (규칙 4): `profiles`에서 이 팀 소속이면서 대상 주 업무가 0건인 사람을 "업무 없음"으로 표시한다. 현재 기획팀은 프로필이 0명이라 팀 전체가 여기에 걸린다.
- **출처 표시** (규칙 7): 각 항목에 task 상세 링크를 단다. 수기 절차의 `파일명:줄번호`를 대체한다.

### 5.2 전체 주간 보고서

- **경로**: `/report?week=2026-W35`
- **열람 권한**: **admin만.** member는 타 팀 상세를 볼 권한이 없다(PRD 2.1).
- **작성 권한** (결정 9): **admin만.** 열람 권한과 같다.
- **구성**: 5.1과 같은 순서에 팀 축이 하나 더 붙는다.
- **프로젝트별 묶음은 팀 교차 집계를 하지 않는다** (결정 7). 프로젝트가 팀에 종속되므로 팀별 프로젝트 목록을 나란히 나열한다. 팀이 달라도 이름이 같은 프로젝트는 합치지 않는다.
- **집계 함수**: 기존 `get_dashboard_summary_stats`는 주차 개념이 없어 그대로 쓸 수 없다. 대상 주차를 받는 함수를 새로 만든다.

### 5.4 Word 내보내기 (결정 11)

- **경로**: `GET /api/reports/docx?week=2026-W35&scope=TEAM&team=development`
- **열람 권한**: 화면과 같다. `weekly_reports` RLS가 강제하므로 권한이 없으면 행이 조회되지 않고 404가 나간다.
- **문서 순서는 화면과 같다** (규칙 15). 두 렌더러가 같은 `payload`를 읽는다. Word 쪽에서 집계를 다시 하지 않는다.
- **구현**: `docx` 패키지로 실제 .docx를 만든다. HTML을 .doc 확장자로 내보내는 방식을 쓰지 않는다.
- 파일명은 `2026-W35_개발팀_주간업무보고서.docx` 형태다. 한글 파일명은 RFC 5987로 넘기고 ASCII 대체 이름을 함께 준다.

### 5.3 공통 UI 규칙

- **요약 영역** (결정 4): 자동 생성 직후에는 비어 있다. 작성 전에는 "요약 미작성" 상태를, 작성 후 확정 전에는 "미확정" 상태를 표시한다. AI 초안 배지는 쓰지 않는다.
- **확정 버튼**: `DRAFT` → `CONFIRMED`. 확정 이후에는 자동 재생성이 덮어쓰지 않는다.
- **문체** (규칙 17~20): 자동 생성되는 집계 문장은 짧게, 한 항목 두 줄 이내, 추측 표현("~로 보인다") 금지, 완료는 과거형·진행중은 현재형. 사람이 쓰는 요약란에도 같은 안내를 붙인다.
- **프로젝트 관리**: 3.1의 `UNIQUE (team_id, name)` 제약이 표기 흔들림을 막으므로 보고서 화면에는 통일 기능이 필요 없다. `projects` 관리 화면에서 이름을 바꿀 때만, 영향받는 업무 건수를 먼저 보여주고 승인을 받는다 (규칙 13).

## 9. 구현 중 발견한 것 (2026-08-31)

기획서를 그대로 옮기다 드러난 문제들이다. 코드는 아래대로 고쳐 넣었고, 해당 절에도 반영했다.

| # | 발견 | 조치 |
|---|---|---|
| 1 | 🔴 4.4의 `UNIQUE (cycle_week, scope, team_id)`가 동작하지 않는다. Postgres는 UNIQUE에서 NULL을 서로 다른 값으로 보므로 `scope='ALL'` 행이 한 주차에 여러 개 생길 수 있다 | 부분 유니크 인덱스 2개 + CHECK 제약으로 대체 (4.4) |
| 2 | 🔴 보고서 생성 RPC 2종이 `SECURITY DEFINER`라 RLS를 우회하는데, Postgres 기본값이 PUBLIC 실행 허용이다. 공개 anon 키만으로 전 팀 업무를 읽을 수 있었다 | `anon`/`PUBLIC`에서 EXECUTE 회수 + 함수 내부 호출자 재확인 (마이그레이션 `130300`) |
| 3 | 🔴 그 호출자 확인이 처음엔 열린 채로 실패했다. `auth.role()`이 NULL이면 조건 전체가 NULL이 되고 `IF NOT NULL THEN`은 본문을 실행하지 않는다 | `COALESCE`로 false 보장 + 호출부는 `IS NOT TRUE`로 검사 |
| 4 | 🟡 팀장 역할이 DB에 없다. `profiles.role`은 `member`/`admin` 2종뿐이다 | 결정 9로 팀장 개념을 두지 않기로 확정 (5.1) |

### 미해결 — 확인이 필요한 항목

| # | 항목 | 상태 |
|---|---|---|
| 1 | 🔴 **cron 자동 생성에는 `SUPABASE_SERVICE_ROLE_KEY`가 필요하다.** 현재 설정되어 있지 않다 | 마감은 정상 실행된다. 보고서 생성만 건너뛰고, 그 사유를 응답과 로그에 남긴다. 조용히 넘어가지 않는다 |
